## Scope

### Must-haves
- Screen 2 split layout: left = chat (agent Q&A), right = live catalog table
- Agent fires an opening message automatically on page load (no user prompt needed)
- Right panel pre-populated with starter catalog derived from raw profile (column names, inferred types, sample values) — before any user interaction
- Context Agent with 5 tools
- Agent asks ≤2 questions per turn, updates catalog immediately after each response
- Catalog keyed by `slug` (filename-derived, human-readable) — catalog entries are identifiable in SQLite without needing to know the raw UUID
- "Mark Complete" button → direct navigation to Query Canvas (no background job, no transition state)

### Nice-to-haves (only if time allows)
- FK entries rendered as linked badges (`→ orders.user_id`)
- Confidence styling: columns the agent inferred without asking shown in muted/italic style
- Table dropdown if the uploaded CSV maps to multiple logical tables

## Catalog Identification

Every catalog entry is stored with both `upload_id` (UUID) and `slug` (human-readable). The slug is derived from the filename at upload time:

```
"orders_2024.csv"      → slug: "orders_2024"
"my sales data.csv"    → slug: "my_sales_data"
"Q3-Revenue Report.csv"→ slug: "q3_revenue_report"
```

Rule: lowercase, strip extension, replace spaces/special chars with `_`, collapse repeated `_`.

This means a catalog entry in SQLite always shows a recognisable label (`orders_2024`) alongside the raw UUID — making the database human-navigable during development and demo.

## Starter Catalog Population

When Screen 2 loads, before the agent says anything, the right panel shows a populated catalog. This is built from the raw profile at upload time (no LLM involved):

- Column name (from CSV header)
- Data type (inferred by pandas: TEXT / INTEGER / REAL / DATETIME)
- Sample values (3 random non-null values)
- Null % (from profile)
- Inferred role (heuristic, not LLM):
  - Column name ends in `_id` or `id` → `identifier`
  - Dtype is datetime → `datetime`
  - Dtype is numeric, column name contains keywords (revenue, amount, count, price, qty) → `measure`
  - All other columns → `dimension`

These starter rows are written to the `catalog` table during the upload pipeline (after coercion), so `GET /api/context/{id}/catalog` always returns something on first load.

## Context Agent

**Pattern:** LangGraph single-node agent with tool-calling loop. Runs synchronously per turn.  
**Trigger:** Frontend POSTs `{ message: "__INIT__" }` on page load to get the opening message.  
**State:** Full conversation history passed on every turn (read from `context_conversations` table).

### Role Persona
> "You are a senior data analyst onboarding a new dataset for the first time. Your job is to interview the data owner to build a complete semantic catalog — understanding not just what columns are named, but what they mean, how they relate, what business concepts they represent, and what quirks exist. You ask precise, targeted questions. You never ask more than 2 questions at a time. You update the catalog as you learn. You never ask about things you can confidently infer."

### Tools

```python
get_dataframe_profile(upload_id: str) -> dict
    # Returns shape, dtypes, null counts, nunique per column, basic stats.
    # Called once at conversation start to ground the agent.

sample_column_values(upload_id: str, column_name: str, n: int = 10) -> list
    # Returns n random non-null sample values from a column.
    # Agent uses this before asking about a column — so questions are
    # specific: "I can see values like 'TXN_2024_001' — is this a
    # transaction ID generated by your system?" rather than generic.

infer_relationships(upload_id: str) -> list[dict]
    # Heuristic FK detection: finds columns with overlapping value sets.
    # Returns: [{ col_a, col_b, overlap_pct, suggested_relation }]
    # Agent uses this to ask: "customer_id appears to relate to id
    # in another table — can you confirm this?"

write_catalog_entry(
    upload_id: str,
    column_name: str,
    updates: dict    # any subset of catalog fields
) -> bool
    # Writes/updates a single catalog row in SQLite.
    # Agent calls this after EVERY confirmed piece of information.
    # This is what causes the right-panel to update after each turn.

mark_catalog_complete(upload_id: str) -> bool
    # Sets uploads.context_complete = TRUE.
    # Agent calls this when satisfied it has enough context,
    # or when user says "done" / "that's enough".
```

### Conversation Flow

1. **Opening turn** (triggered by `__INIT__` message):
   - Agent calls `get_dataframe_profile` + `infer_relationships`
   - Identifies the 2–3 most ambiguous columns
   - Calls `sample_column_values` on each
   - Writes what it can confidently infer to catalog (no questions about `created_at` datetime columns, obvious PKs, etc.)
   - Asks exactly 2 questions about the most ambiguous columns

2. **Each subsequent turn**:
   - Calls `write_catalog_entry` for everything confirmed in the user's response
   - Calls `sample_column_values` on any new column it wants to ask about
   - Asks ≤2 new questions

3. **Completion** (after 4–6 exchanges, or when user says "done"):
   - Summarises what was learned
   - Calls `mark_catalog_complete`
   - Returns a completion message (frontend "Mark Complete" button becomes active)

### What the Agent Never Asks About
- Columns it can confidently infer from name + type + samples (e.g. `created_at` datetime, `id` integer PK)
- Things the user already answered in prior turns

### Turn Response Contract

The context agent response extends the base Pattern B shape with two extra keys. `catalog` is returned alongside `canvas` (not inside it) to keep the shared `CanvasResponse` contract clean.

```json
{
  "chat": "Got it — revenue is pre-tax USD. I've updated the catalog. Next: is customer_id unique per customer, or can one customer have multiple IDs across orders?",
  "canvas": {
    "insights": [],
    "charts": [],
    "table": null
  },
  "catalog": [
    {
      "column_name": "revenue",
      "data_type": "REAL",
      "inferred_role": "measure",
      "business_context": "pre-tax USD",
      "description": "Total order revenue before tax",
      "is_primary_key": false,
      "is_foreign_key": false,
      "foreign_key_ref": null,
      "sample_values": ["120.00", "340.50", "89.99"]
    }
  ],
  "complete": false
}
```

- `catalog` is the full current catalog state — all columns, not just the updated one. Frontend replaces the right panel on every response.
- `complete: true` is set when the agent calls `mark_catalog_complete`. Frontend uses this to activate the "Mark Complete" button.

## API Endpoints

```
POST /api/context/{upload_id}/chat
  Body: { message: string }   -- "__INIT__" for opening turn
  Response: { chat: string, canvas: CanvasResponse, catalog: CatalogRow[], complete: boolean }
  Side effects:
    - Reads full conversation history from context_conversations
    - Runs agent (synchronous — each turn is <5s)
    - Agent calls write_catalog_entry → updates catalog table
    - Saves user message + agent response to context_conversations

GET /api/context/{upload_id}/catalog
  Response: { slug: string, columns: CatalogRow[] }
  Used by: Screen 2 initial load (before first chat turn)

POST /api/context/{upload_id}/complete
  Response: { ok: true }
  Side effects:
    - Sets uploads.context_complete = TRUE (if agent hasn't already)
    - No job created, no background work
```

### State Flow

1. Page loads → `GET /api/context/{uploadId}/catalog` → populate right panel with starter catalog
2. Immediately POST `{ message: "__INIT__" }` → get agent's opening message → render in chat
3. User types response → POST chat → show loading → on response: update chat + replace catalog panel
4. Repeat until response includes `complete: true` (agent called `mark_catalog_complete`)
5. "Mark Complete" button activates → user clicks → `POST /api/context/{id}/complete` → navigate to `/query`
